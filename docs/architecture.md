## Компоненты

| Компонент | Файлы | Назначение |
| --- | --- | --- |
| Точка входа | `app.py` | FastAPI-приложение, жизненный цикл (проверка настроек, инициализация базы, сид/каталог), заголовки безопасности, раздача фронтенда и страницы-портала, запуск `uvicorn.run` |
| Настройки | `backend/config.py` | `Settings` из переменных окружения, проверка при старте |
| HTTP API | `backend/api.py` | Маршруты `/api/*`, тела запросов (pydantic), зависимость `get_context` |
| Авторизация | `backend/security.py` | Проверка подписи `initData`, формирование `Identity` |
| Логика | `backend/service.py` | Пользователи, роли, сборка состояния, действия (задания, проверка, магазин) |
| Регистрация школ | `backend/registration.py` | Школы, классы, коды, подтверждение школ, лимиты |
| Правила игры | `backend/game.py` | Уровни, категории, косметика, достижения, даты, начисление XP |
| База | `backend/db.py` | Схема, подключение, миграции |
| Лимиты | `backend/ratelimit.py` | Скользящее окно в памяти процесса |
| Каталог | `backend/catalog.py` | Необязательный импорт школ из `catalog.json` |
| Демо-данные | `backend/demo_seed.py` | Выдуманные данные, только `APP_MODE=demo` |
| Фронтенд | `frontend/src/` | React + TypeScript, сборка Vite в `static/` |
| Страница-портал | `landing/` | Статический HTML, маршруты `/portal`, `/landing`, `/about` |
| Развёртывание | `deploy/`, `Dockerfile`, `docker-compose.yml`, `docker/Caddyfile` | См. [deploy.md](deploy.md) |

Схема:

```text
MAX (клиент) -> HTTPS -> nginx (app.example.org) -> uvicorn 127.0.0.1:8000 -> FastAPI (app.py)
                                                   |- /api/*     -> backend/api.py -> service.py / registration.py -> SQLite
                                                   |- /portal    -> landing/index.html
                                                   `- остальное  -> static/ (SPA) при SERVE_FRONTEND=true
```

Приложение - один процесс. Обработчики API объявлены как обычные функции (`def`), поэтому FastAPI выполняет их в пуле потоков. Состояния между запросами в памяти нет, кроме счётчиков лимитов (см. [Ограничения](#ограничения)).

Маршрутизация в `app.py`: `/api/*` обрабатывает роутер; `/portal`, `/landing`, `/about` и `/landing/<файл>` отдают файлы из `landing/`; `/` и любой другой путь без расширения отдают `static/index.html` (SPA-фолбэк), пути с расширением - файл из `static/` или 404. При `SERVE_FRONTEND=false` `/` возвращает JSON-заглушку, остальные пути вне `/api` - 404. `/docs`, `/redoc` и `/openapi.json` отключены при `APP_MODE=prod` (404, в том числе при `SERVE_FRONTEND=true`); в demo и sandbox они доступны.

Заголовки ответа: `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`, `Content-Security-Policy: frame-ancestors 'self' https://max.ru https://*.max.ru`; `/assets/*` - `Cache-Control: public, max-age=31536000, immutable`; `/` и `/api/*` - `no-store`.

## Поток запроса и авторизация

Для каждого запроса к `/api/*`, кроме `/api/health`, зависимость `get_context` (`backend/api.py`):

1. Открывает **новое** соединение SQLite (`connect`: `foreign_keys=ON`, `busy_timeout=15000`, `synchronous=NORMAL`, `row_factory=Row`).
2. Читает заголовки `X-Max-Init-Data` и `X-Client-Id`.
3. `identity_from_request` строит `Identity` (см. ниже). Ошибка - ответ `401` с текстом ошибки в `detail`.
4. `ensure_user` находит или создаёт строку `users`, обновляет имя/username/фото из подписанных данных, повышает роль по спискам id.
5. Обработчик вызывает функцию сервиса, делает `commit` и возвращает `{"state": ...}` (почти всегда).
6. Соединение закрывается.

Ошибки бизнес-логики - исключение `GameError(message, status)`, превращается в `{"detail": message}` с указанным статусом. Ошибки валидации тела запроса - стандартный `422` FastAPI.

### Подписанный initData (режим `prod`)

`backend/security.py`, `validate_init_data`. Клиент передаёт сырую строку `window.WebApp.initData` в заголовке `X-Max-Init-Data`. Небезопасное `initDataUnsafe` не используется.

1. Строка разбирается как query-string (`parse_qsl`, пустые значения сохраняются). Должно быть ровно одно поле `hash`.
2. Строка проверки: все пары, кроме `hash`, в виде `key=value`, отсортированные и склеенные символом `\n`.
3. Секрет: `HMAC_SHA256(key="WebAppData", msg=MAX_BOT_TOKEN)`.
4. Подпись: `HMAC_SHA256(key=секрет, msg=строка проверки)`, hex. Сравнение через `hmac.compare_digest`.
5. `auth_date` обязателен и целый. Отклоняется, если он больше «сейчас + 60 с» (из будущего) или старше `INIT_DATA_MAX_AGE` (по умолчанию 86400 с).
6. Из поля `user` (JSON) берётся `id` (становится `max_user_id`), а также `first_name`, `last_name`, `username`, `photo_url` (обрезаются до 64/64/64/512 символов).
7. Роль-подсказка: id в `DIRECTOR_MAX_IDS` - `director`; иначе в `TEACHER_MAX_IDS` - `teacher`; иначе `student`.

Возраст проверяется на каждый запрос, а клиент повторно отправляет одну и ту же строку `initData` из MAX Bridge. Поэтому в сеансе, который открыт дольше `INIT_DATA_MAX_AGE`, запросы получат `401` «Данные MAX устарели», пока приложение не откроют заново. Фронтенд в этом случае показывает экран «Сессия устарела» с кнопкой «Обновить» и не повторяет запросы.

Ошибки `401` (тексты на русском): нет данных авторизации; нет токена на сервере; некорректная подпись; подпись не совпадает; нет/некорректный `auth_date`; данные из будущего; данные устарели; нет пользователя в данных.

### Правила создания и обновления пользователя

- Новый пользователь `prod`: роль из подсказки; `onboarded=1` для педагога и директора, `0` для ученика; 40 искр; образ по умолчанию; `class_id` - класс педагога из `class_staff` (для педагога) либо `DEFAULT_CLASS_ID`.
- Существующий: подтягиваются имя, username, фото. Роль только **повышается** (`student < teacher < director`); списки id роль не понижают, а директор, созданный регистрацией, не понижается списком педагогов. Удаление id из `.env` роль не снимает; средства снятия роли в коде нет.
- Для существующего педагога из списка: класс из каталога (`class_staff`) принудительно применяется; без записи в каталоге `DEFAULT_CLASS_ID` подставляется только если у него нет класса.
- Директор из `DIRECTOR_MAX_IDS` при заданном `DEFAULT_CLASS_ID` получает запись `school_staff` для школы этого класса. Без `DEFAULT_CLASS_ID` такой директор не привязан ни к одной школе и видит заглушку «Школа не подключена».

## Определение личности по режимам

| Режим | Что читается | Результат |
| --- | --- | --- |
| `prod` | `X-Max-Init-Data` (подпись обязательна). `X-Client-Id` игнорируется | `Identity(kind="max")`, ключ пользователя - `users.max_user_id` |
| `demo` | `X-Client-Id` должен соответствовать `^[A-Za-z0-9_-]{8,64}$`, `initData` игнорируется | Всегда один и тот же пользователь: `client_id` подменяется константой `demo-viewer`, имя «Глеб Кузнецов». Так посетители не плодят копии ученика в рейтинге |
| `sandbox` | `X-Client-Id` с тем же шаблоном, `initData` игнорируется | `Identity(kind="sandbox")`, ключ пользователя - сам `X-Client-Id` (`users.client_id`). Каждый id - отдельный пользователь с ролью ученика, имя «Герой», 40 искр. Роли списками id не назначаются (`role_hint` всегда `student`); ролями становятся через регистрацию школы и коды |

Некорректный или отсутствующий `X-Client-Id` в `demo`/`sandbox` - `401`. В `sandbox` администратор платформы определяется по `PLATFORM_ADMIN_CLIENT_IDS` (в `prod` - по `PLATFORM_ADMIN_MAX_IDS`). Запрет запуска вне loopback и очистка базы при старте описаны в [configuration.md](configuration.md) и [development.md](development.md).

Фронтенд: если у моста MAX есть `initData`, он отправляет `X-Max-Init-Data`; иначе - `X-Client-Id` (идентификатор из `localStorage`). В `prod` вне MAX интерфейс показывает «Откройте приложение внутри MAX» и запросов состояния не делает. В `sandbox` фронтенд подставляет `X-Client-Id` активного тестового пользователя панели «Песочница».

## Схема базы данных

SQLite, файл по [пути данных](configuration.md#пути-данных). Режим журнала WAL (рядом файлы `-wal` и `-shm`). Время хранится в UTC строкой `YYYY-MM-DD HH:MM:SS`; сроки заданий (`challenges.deadline`) - ISO-строка со смещением `+03:00`.

```text
schools 1---N classes 1---N users (role=student/teacher; class_id)
   |               |  \
   |               |   `--N challenges 1---N completions N---1 users
   |               `--- class_staff (max_user_id -> class_id)
   `--- school_staff (user_id, school_id): директора школ
users 1---N xp_events,  users 1---N activity_days
```

| Таблица | Назначение | Основные поля и ограничения |
| --- | --- | --- |
| `schools` | Школы | `name`, `city`, `status` (`active`/`pending`/`rejected`), `created_by` -> users, `created_at`, `norm_key` (регистронезависимый ключ `название|город`). `UNIQUE(name, city)`, уникальный индекс по `norm_key` |
| `classes` | Классы | `school_id`, `name`, `weekly_goal` (по умолчанию 1600), `invite_code` (код ученика), `teacher_code` (код педагога). `UNIQUE(school_id, name)`, уникальные частичные индексы по кодам |
| `users` | Пользователи | `max_user_id` (уникален), `client_id` (уникален, demo/sandbox), имя, `role` (`student`/`teacher`/`director`), `preview_role` (демо), `class_id`, `school_id` (активная школа директора), `xp`, `sparks`, `streak`, `last_active_date`, `avatar` (JSON), `owned` (JSON-список купленных предметов), `onboarded` |
| `challenges` | Задания класса | `class_id`, `title`, `description`, `category`, `xp` (10..300 по API; в БД CHECK 1..500), `kind` (`daily`/`weekly`/`event`), `deadline`, `subject`, `proof_type` (`text`/`link`/`photo`), `created_by`, `active` (0 = в архиве) |
| `completions` | Выполнения | `user_id`, `challenge_id`, `status` (`pending`/`approved`/`rejected`), `proof`, `proof_url`, `reviewed_at`, `reviewed_by`, `reject_reason`. `UNIQUE(user_id, challenge_id)` - одна запись на пару, повторная отправка после отклонения обновляет её |
| `xp_events` | Журнал начисления XP | `user_id`, `amount`, `reason`, `category`, `created_at`. Источник недельного XP и ленты класса |
| `class_staff` | Назначения педагогов из каталога | `max_user_id` (PK), `class_id`. Заполняется только из `catalog.json` |
| `school_staff` | Директора школ | `(user_id, school_id)` PK. Определяет, какие школы директор может видеть и менять |
| `activity_days` | Дни активности | `(user_id, day)` PK. Источник полоски серии за 7 дней |

Прочее: пользователи и школы не удаляются ни одним маршрутом; класс можно удалить, только если в нём нет пользователей и заданий (включая архивные).

## Миграции

Системы версий миграций нет. При каждом старте `init_db`:

1. Выполняет `SCHEMA` (`CREATE TABLE IF NOT EXISTS`, `PRAGMA journal_mode=WAL`).
2. `_migrate_columns` добавляет недостающие колонки через `ALTER TABLE` (`subject`, `proof_type`, `proof_url`, коды классов, `school_id`, поля школы).
3. Если у `schools` старое ограничение `UNIQUE(name)`, таблица пересоздаётся с `UNIQUE(name, city)`.
4. Заполняет `norm_key` для школ, где он пуст (дубликаты остаются с `NULL`).
5. Создаёт индексы; уникальные индексы по кодам и `norm_key` создаются «по возможности»: при конфликте в старых данных индекс пропускается без ошибки.

Все шаги идемпотентны. Для изменения схемы добавляйте `CREATE TABLE IF NOT EXISTS` в `SCHEMA` или проверку колонки в `_migrate_columns`; откатов нет, перед обновлением делайте резервную копию ([deploy.md](deploy.md)).

## Гардероб и образ героя

- Каталог предметов - `COSMETICS` в `backend/game.py`; он же источник правил (уровень, цена, слот, редкость). `GET /api/state` отдаёт его в `cosmetics` вместе с флагами `owned`, `unlocked`, `equipped`.
- Образ героя хранится в `users.avatar` как JSON по слотам: `skin`, `hair`, `hairColor`, `outfit`, `hat`, `face`, `accessory`, `frame`. `load_avatar` подставляет значения по умолчанию для отсутствующих или неподходящих по слоту ключей, поэтому старые записи работают без миграции. `validate_avatar_patch` проверяет слот, уровень и покупку.
- Герой и магазин доступны только ученикам (`_require_student_hero` в `service.py`).
- Фронтенд рисует героя по id: `components/PixelHero.tsx` (тело, волосы, цвета) и `components/heroItems.tsx` (одежда, шапки, лицо, аксессуары) на сетке 32x42; рамки - `components/AvatarFrame.tsx` + `styles/frames.css`.
- Экран «Стиль» (`screens/WardrobeScreen.tsx`) - «летающая камера»: CSS transform на обёртке, кадр вычисляется из геометрии сетки (`HERO_PARTS`) и размера сцены.

## Роли и права

Роль хранится в `users.role`. В демо эффективная роль берётся из `preview_role` (`effective_role`).

| Действие | Ученик | Педагог | Директор | Админ платформы |
| --- | --- | --- | --- | --- |
| Видеть задания своего класса, отправлять выполнение | да | нет (403 при отправке) | нет в интерфейсе; API проверяет только класс | - |
| Проверять заявки (`approve`/`reject`), в том числе пакетно | нет (403) | свой класс | классы своих школ (API) | - |
| Создавать и архивировать задания | нет (403) | свой класс | классы своих школ (API) | - |
| Начислять XP ученику (10-300) | нет | свой класс | классы своих школ (API) | - |
| Магазин, образ, профиль | да | API не запрещает | API не запрещает | - |
| Создать школу | любой аккаунт (кроме `demo`) | то же | то же | - |
| Классы, коды, выбор школы | нет | нет | свои школы | - |
| Подтвердить/отклонить школу | нет | нет | нет | да |

«Админ платформы» - это не роль в `users.role`, а признак по MAX id из `PLATFORM_ADMIN_MAX_IDS` (в `sandbox` - по `PLATFORM_ADMIN_CLIENT_IDS`); к любой роли добавляет вкладку «Заявки».

Пояснения:

- Интерфейс директора не содержит экранов проверки и создания заданий; эти действия доступны директору только через API.
- Права педагога определяются `class_id` пользователя; директора - строками `school_staff`. Проверка `can_manage_class` применяется ко всем действиям с чужими данными.
- Педагог привязан ровно к одному классу. Отзыва прав педагога и смены его класса директором нет.

Подробнее по интерфейсу: [roles.md](roles.md). Подключение школы: [setup-school.md](setup-school.md).

## Изоляция школ

- Данные, зависящие от класса (задания, лента, состав класса, очередь проверки), выбираются по `class_id` зрителя.
- Директор получает данные только по школам из `school_staff`. Чужая школа или класс - `404` «Школа не найдена»/«Класс не найден». Для демо эти маршруты закрыты.
- Педагог и директор действуют только в `can_manage_class`.
- Ученик другого класса не может отправить выполнение чужого задания (403).
- Школы со статусом не `active` не попадают в каталог, коды таких школ не принимаются, а их классы не видны в рейтингах никому, кроме своей школы.
- Коды приглашения никогда не попадают в публичный каталог `/api/school/catalog`.

Что видно между школами намеренно: рейтинг классов и школ (название, город, XP, число учеников) доступен всем авторизованным пользователям, как и каталог активных школ и классов. Списки учеников даются только по своему классу.

Код ученика не является ограничением доступа: `class_id` из каталога можно передать в `/api/onboarding` или `/api/school/join` без кода, и ученик попадёт в любой класс любой активной школы.

## Состояние /api/state

`GET /api/state` (и поле `state` в ответах мутаций) собирает всё состояние зрителя целиком: клиент не делает отдельных запросов за данными. Побочные эффекты: запрос создаёт пользователя при первом обращении, а для директора добирает недостающие коды классов у классов, импортированных из старого каталога.

| Поле | Содержимое |
| --- | --- |
| `mode`, `verified`, `today` | режим, признак подписанного входа, дата по Москве |
| `viewer` | профиль: id, имя, роль, класс, школа (`school_status`), город, `invite_code` класса, `is_platform_admin`, XP, уровень, искры, серия, образ, купленное, `onboarded`, недельный XP, места в классе/школе/личное, статистика, `to_next` |
| `class_sprint` | цель недели класса: XP за неделю, цель, процент, место, число учеников, лидер недели |
| `challenges` | активные задания класса зрителя со статусом зрителя: `available`, `pending`, `approved`, `rejected`, `expired`; число участников и заявок |
| `leaderboard` | `students` (весь класс), `classes`, `schools` (первые 100 и класс/школа зрителя) |
| `feed` | последние 12 начислений XP в классе |
| `week` | последние 7 дней с флагом активности |
| `achievements`, `cosmetics` | достижения с прогрессом; каталог предметов с флагами `owned`/`unlocked`/`equipped` |
| `teacher` | только для педагога с классом: очередь заявок, ученики с рисками и историей, статистика, график недели, задания |
| `director` | только для директора со школой: KPI, параллели, направления, таблица классов |
| `school_admin` | для директора: школы, классы, коды, лимиты |
| `platform_admin` | для админа платформы: режим подтверждения и до 100 ожидающих школ |
| `demo_teacher_available`, `demo_director_available` | `true` в `demo` |

## XP, уровни, искры

- XP начисляется только при подтверждении заявки педагогом (награда задания) или при ручном начислении педагогом (`/api/teacher/reward`, 10-300). Ученик сам XP не получает.
- Уровни (`RANKS` в `backend/game.py`): 1 «Новичок» с 0; 2 «Ученик» со 100; 3 «Знаток» с 250; 4 «Мастер» с 450; 5 «Легенда школы» с 700.
- Искры: 40 стартовых (кроме `demo`), +5 за каждое подтверждённое задание или ручное начисление, +25 за каждый полученный уровень. Тратятся на предметы с ценой (`hoodie_cyan` 40, `cap` 50, `frame_galaxy` 80). Остальные предметы открываются уровнем.
- Серия: подряд идущие дни (по Москве), в которые ученик отправил задание, получил подтверждение или ручное начисление.
- Награды заданий: педагог задаёт любое целое от 10 до 300 XP (проверка в `create_challenge` и в схеме API). Словарь `XP_VALUES` в `game.py` в расчётах не участвует.
- Срок: дата `YYYY-MM-DD` превращается в 23:59 по Москве; без даты - через 2 дня. После срока отправка невозможна (`Срок выполнения уже истёк`). Отклонённое задание можно отправить заново (пока срок не прошёл).
- Достижения (`ACHIEVEMENTS`): «Первый шаг» (1 подтверждённое), «Свой среди своих» (3 подтверждённых в категории `help`), «Олимпиец» (1 в `olympiad`), «Неделя силы» (серия 7), «Мастер» (уровень 4), «Командный дух» (класс в топ-3 по общему месту среди классов).

## Рейтинги и показатели

- Неделя: с понедельника 00:00 по UTC+3. Недельный XP - сумма `xp_events` за неделю.
- Рейтинг класса: сумма XP учеников (`role='student'`), по убыванию, при равенстве - по id класса. Места глобальные, среди всех активных школ (и своей школы зрителя, даже если она не подтверждена). В ответ попадают первые 100 и класс зрителя.
- Рейтинг школ: сумма XP их классов, при равенстве - по названию; то же ограничение 100.
- Личный рейтинг: ученики класса по XP, без ограничения.
- `progress` в рейтингах - процент от лидера. В таблице классов директора сортировка по недельному XP, затем по XP, а `progress` - недельный XP к цели класса (не более 100).
- Вовлечённость: ученики с недельным XP > 0 к общему числу учеников.
- «Направления» директора считаются по подтверждённым заданиям: `homework`, `weekly` - учебно-исследовательское; `olympiad` - олимпиадное; `event` - гражданско-патриотическое; `club` - ЗОЖ, спорт и творчество; остальные (`help`, `streak`) - волонтёрство. Ручные начисления сюда не входят. `social_activity_index` = число заданий волонтёрства + XP волонтёрства // 10.
- «Требуют внимания» у педагога: нет активности 3 и более дней (или никогда) либо есть отклонённые работы.

## Ограничения

- Лимиты в памяти процесса (`backend/ratelimit.py`): неверные коды - 20 за 10 минут на пользователя; создание школы - 5 попыток в час на пользователя. Ключ включает путь к базе и id пользователя. Перезапуск обнуляет счётчики; несколько процессов считают раздельно (фактический лимит умножается на число процессов).
- SQLite: одна база-файл, один писатель; при записи другие ждут до 15 секунд (`busy_timeout`).
- Состояние собирается заново на каждый запрос, включая агрегаты по всем классам для рейтингов. Измерений производительности в репозитории нет.
- Часовой пояс фиксирован (Москва).
- Достижение «Командный дух» описано как «топ-3 города», но считается по месту среди всех классов платформы.
